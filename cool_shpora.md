# Шпора: командная работа с GitHub через Pull Request

Эта инструкция для участников команды, которые работают с общим
репозиторием на GitHub через консоль Git.

## 1. Один раз: получить проект

Если у тебя ещё нет локальной копии проекта:

```bash
git clone https://github.com/Ikarych1/Software_engineering-KPO-_Chur.git
cd Software_engineering-KPO-_Chur
```

Если проект уже клонирован, просто перейди в его папку:

```bash
cd Software_engineering-KPO-_Chur
```

Если у тебя был локальный репозиторий, связанный с гитхабным со старым названием - поменяй ссылку на текущую

```bash
git remote -v 
git remote set-url origin https://github.com/Ikarych1/Software_engineering-KPO-_Chur
```

Проверь состояние и удалённый репозиторий:

```bash
git status
git remote -v
git branch
```

## 2. Перед началом каждой задачи: обновить `main`

```bash
git switch main
git pull origin main
```

## 3. Создать отдельную ветку для своей задачи

Назови ветку по смыслу задачи. Например:

```bash
git switch -c feature/update-readme
```

Другие примеры названий: `fix/login-error`, `docs/sql-examples`.

**Не работай над своей задачей прямо в `main`.** Каждый участник делает
изменения в собственной ветке.

## 4. Изменить файлы и сохранить коммит

Отредактируй нужные файлы любым редактором, затем проверь изменения:

```bash
git status
git diff
```

Добавь нужные файлы и создай коммит:

```bash
git add README.md
git commit -m "Update project README"
```

Если изменено несколько конкретных файлов, перечисли их в `git add`.
Команда `git add .` тоже возможна, но сначала проверь `git status`,
чтобы случайно не включить лишние файлы.

Убедись, что коммит создан:

```bash
git log --oneline -3
git status
```

## 5. Отправить свою ветку на GitHub

```bash
git push -u origin feature/update-readme
```

При первом `push` для новой ветки используй `-u`. В следующих отправках
обычно достаточно:

```bash
git push
```

## 6. Создать Pull Request (PR) на GitHub

1. Открой общий репозиторий на GitHub в браузере.
2. Создай Pull Request: **base** --- `main`, **compare/head** --- твоя
   ветка `feature/update-readme`.
3. Напиши понятный заголовок и кратко опиши, что изменено и как это
   проверить.
4. Создай PR и отправь ссылку участнику команды, который проверяет
   изменения.

Pull Request --- это запрос на включение изменений из твоей ветки в
`main`. Сам по себе PR ещё не означает, что изменения уже попали в
основную ветку.

Если GitHub предлагает кнопку **Compare & pull request** после `push`,
можно нажать её.

## 7. Проверка и слияние PR

Проверяющий участник должен посмотреть изменения на вкладке **Files
changed**, оставить комментарии при необходимости и одобрить изменения
согласно правилам команды.

После проверки PR сливают кнопкой **Merge pull request** (или другим
разрешённым командой способом).

Если у участника нет прав на создание веток в общем репозитории, нужно
сделать **Fork** на GitHub, клонировать свой форк и отправлять ветку в
него. Затем PR создаётся из ветки форка в основной репозиторий команды.
Если прав хватает, форк не нужен.

## 8. После слияния PR: обновить локальную копию

После того как PR принят и слит в `main`:

```bash
git switch main
git pull origin main
```

Когда твоя ветка больше не нужна, можно удалить её локально:

```bash
git branch -d feature/update-readme
```

Удаление локальной ветки необязательно. Удалённую ветку на GitHub можно
удалить после слияния через интерфейс PR, если команда так договорилась.

## 9. Если в `main` появились новые изменения, пока ты работал

Сначала сохрани свою работу коммитом. Затем подтяни свежий `main` и
обнови свою ветку:

```bash
git switch main
git pull origin main
git switch feature/update-readme
git merge main
```

Если возникнут конфликты, Git укажет конфликтующие файлы. Открой их,
найди разделители `<<<<<<<`, `=======`, `>>>>>>>`, вручную оставь
правильный итоговый вариант, затем выполни:

```bash
git add CONFLICTED_FILE
git commit
git push
```

После этого обнови PR: он связан с веткой и обычно обновляется
автоматически после `push`.

Не используй `git push --force` в общей ветке и не выполняй
`git reset --hard`, если не уверен, что понимаешь последствия.

## 10. Полный короткий сценарий для каждой задачи

```bash
git switch main
git pull origin main
git switch -c feature/my-task

# Отредактируй файлы
git status
git diff
git add FILE
git commit -m "Describe my change"
git push -u origin feature/my-task
```

Затем создай PR на GitHub: `feature/my-task` → `main`. Дождись проверки
и слияния. После слияния обнови `main` локально.

## Важные правила команды

- Один участник --- одна рабочая ветка на задачу.
- Не коммить напрямую в `main`, если команда договорилась работать
  через PR.
- Перед началом задачи обновляй `main`.
- Пиши понятные сообщения коммитов и описания PR.
- Не включай в коммиты пароли, токены, `.env` и другие секреты.
- Если `git status` показывает незакоммиченные изменения, не
  переключайся и не удаляй ветки вслепую: сначала разберись, что
  именно изменено.
