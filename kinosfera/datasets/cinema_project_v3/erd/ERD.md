# Общая ERD проекта и тестовой базы v3

**30 таблиц, 203 поля, 40 SQL FK и 10 логических связей без SQL-ограничения.** Дополнительно существует вычисляемое представление `episode_activity`.

Схема извлечена из фактического SQLite-файла и сверена с `.local/cinema.sqlite3`: поля, типы, defaults, PK, UK, индексы, FK и представление совпадают. Это схема работающего проекта с применённым совместимым расширением, а не отдельная аналитическая модель.

- [index.html](index.html) — обзор и семь разделов, масштабирование и печать.
- [cinema_test.drawio](cinema_test.drawio) — редактируемые таблицы и поля diagrams.net.
- [cinema_test.dbml](cinema_test.dbml), [cinema_test_full.mmd](cinema_test_full.mmd) — текстовые схемы с фактически объявленными SQL FK.
- [erd_model.json](erd_model.json) — все таблицы, поля, ключи и типы связей; признак `enforced` отличает SQL FK от логической ссылки.
- `00_overview.svg` … `07_imports.svg` — векторные страницы для отчёта.

## Обозначения

PK — первичный ключ, FK — объявленный SQL внешний ключ, UK — одиночная уникальность, LK — логическая ссылка, которая используется проектом, но не объявлена SQL FK. Несколько PK-полей составляют один ключ. Составные UK перечислены в DBML/JSON.

`?` означает допускаемый NULL. Кратности: `||` — ровно один, `○|` — ноль или один, `○<` — ноль или много. Сплошная линия означает участие ссылки в PK дочерней таблицы; пунктир — неидентифицирующую связь. **Серые точечные линии LK не следует считать действующими ограничениями SQLite.**

В старой схеме, например, `ratings.movie_id` связан с `films.id` по смыслу и коду, но SQL FK для него не объявлен. Схема показывает эту особенность честно. Новые таблицы имеют явные FK. Обзор содержит основные связи; все поля и связи показаны на семи подробных страницах. Повторённые справочные сущности помечены «ссылка».

## JSON и форматы проекта

- `films.data` — строго поля dataclass `MediaItem`; `films.art` — оформление и расширенные метаданные.
- `user_state.data` — `watched`, `ratings`, `watchlist`, `clips`, `settings`, `rooms`, `friends`. Эти списки и объекты не изображены как несуществующие SQL-таблицы.
- `rooms.settings` и `rooms.state` — штатные JSON-объекты, первичный ключ комнаты — `code`.
- `users.id`, ссылки на пользователей, `films.id` — INTEGER; события и сеансы могут иметь собственный TEXT ID.
- Временные поля поведения — Unix seconds REAL. `users.created_at` и `films.updated_at` используют штатные текстовые значения UTC.

## Серии и сеансы

`films.episodes` содержит реальные файловые индексы плеера. Новая `episodes` содержит метаданные серии; `file_id` необязателен. Штатная `episode_progress` использует только существующие файлы. Полный прогресс всех серий вычисляет `episode_activity` из `watch_sessions` по последнему сеансу, сумме времени и признаку когда-либо завершённого просмотра.

`watch_sessions.view_id` — уникальная ссылка на штатный `views.id`. Два представления описывают один просмотр; их нельзя складывать как два независимых действия. Аналогично журнал `events` и специализированные таблицы могут отражать одно событие.

Подробное соответствие исходного набора прикладной схеме находится в [README](../README.md), результат сравнения с рабочей базой — в [validation.json](../validation.json). Определения всех физических объектов и индексов находятся в [schema.sql](../schema.sql).
